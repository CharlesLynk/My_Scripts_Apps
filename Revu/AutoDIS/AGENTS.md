## 1. Purpose and goals

AutoDIS (Mbroh Drawing Index Creator) is a WinUI 3 desktop app on .NET 10 (x64 only), packaged as MSIX. It reads a set of drawing-sheet PDFs (one combined PDF or a folder of single-sheet PDFs), finds each sheet's number, discipline and title, and writes a drawing-index PDF (or CSV) with bookmarks and links. Text-layer sheets are read from the embedded text; sheets whose title block has no text layer (CAD lettering drawn as strokes, or scans) are read by OCR (Tesseract). Output is written atomically, so a locked target keeps a `.partial` file.

What the user wants, in priority order (stated across the sessions):
1. **OCR must always run when needed**, including when only part of a set needs it. (Root cause of the original failure: the build shipped without `tessdata`. Now downloaded and verified by the build; see section 8.)
2. **Accuracy of about 95% with the rest flagged** (orange cells + review reasons), not silent errors. Sets have quirky numbering; there are no hard rules about sheet-number shape; the app learns the set's own patterns.
3. **Speed**, scaling with the machine (resource levels) without user knobs. Use proven open-source tools instead of reinventing; test upgrades like a "test fork" that can be rolled back.
4. **One simple lever for quality: a preset** (Fast / Balanced (default) / Thorough). The user does not want per-field models, DPI or other technical settings exposed; an "advanced" toggle may come later.
5. **Minimal manual work, with a good review UI**: the user fixes discipline headings (rename, remove with cascading regroup, split, undo/reset, image previews) rather than individual entries. Planned: edit the final layout (columns, rows per page) with a preview.
6. **UI rules:** pop-ups are real windows (movable, resizable, app icon), no horizontal scroll bars anywhere (text wraps), animations so lists never jump.
7. **Lean repository:** commit only what is needed; rebuildable or public files (OCR models, word list, build output, packages) are downloaded/built, not committed.

## 6. Architecture today (authoritative summary)

1. **Setup.** Copy the set to a local working file once (system copy), read the template (field boxes, page size), start the render helper pool, load the OCR engines (fast `eng`; plus large `eng_best` only for Thorough). Resource level -> worker threads (physical cores based), memory budget, priority.
2. **Per sheet (parallel workers, page order).** Text layer first (PdfPig). Fields with no text are read by OCR from one drawn picture of the field area:
   - Vector route (CAD sheets): `DrawVectorField` draws the field from the page's vector shapes; a 150 DPI probe measures letter height, then the field is drawn at the DPI that gives the target height times the preset's oversample (Fast 1.0, Balanced 1.25, Thorough 1.5; second look 2.0). No PDF renderer involved.
   - Picture route (scans or sheets where vector drawing declines): PDFium renders the field area in a helper process; DPI is capped at 1.5x the scan's own resolution (`NativePictureDpi`) and by the preset's ceiling (300/450/600). Resolution is derived, not a setting.
   - Blank pages are detected and shown as `[BLANK PAGE]`. Half-size or enlarged sheets scale the field boxes (`FieldsForPage`).
3. **Reading** (`OcrFieldRecognizer`): clean the image, bring letters to a fixed height (44 px; Tesseract rescales lines itself, extra pixels only add noise), read variants (titles thickened and thickened+de-slanted; IDs and disciplines untouched first, more variants when doubtful), keep the nearest line to the expected place, try the next-nearest lines if the first does not look like the field, keep all candidates with confidences.
4. **Analysis** (`IndexAnalyzer`, whole index): learn the set (sheet-number profile, disciplines, words, word pairs), choose among candidates by fit to the set, repair numbering from neighbours, series prefixes and letters, misplaced discipline/title, spelling (dictionary + set vocabulary + confusable-letter and merged-stroke rewrites), split words, "NO." numbers, stray marks, lone-zero endings, missing disciplines (series rule, then neighbour rule), then flag everything doubtful with reasons (orange cell; CSV gets a CHECK column).
5. **Second look (Thorough only).** Only fields still doubtful after the analysis are redrawn finer and read with the large model; its readings join the candidates and the analysis runs again.
6. **Review (default on).** Discipline-heading window: rename, remove (regroups following rows), split, undo/reset, preview pictures (pre-rendered in the background through the helper pool; memory only). Then export.
7. **Presets (`OcrPreset.cs`).** Fast: titles read once, 1 retry, 300 DPI ceiling, oversample 1.0. Balanced: two title variants, 3 retries, 450, 1.25. Thorough: Balanced + second look, 600, 1.5. Saved names map Fastest -> Fast and Quality/Ultra -> Thorough.
8. **Resource levels (`ResourcePlan.cs`).** Background / Normal (default) / High / Maximum scale workers (cores/4 .. all physical cores, max 8), render helpers (1 .. 8), memory budget (about 300 MB per worker) and process priority. Measured: throughput stops improving at the physical core count. Server GC is on (PdfPig allocates heavily); Tesseract is single-threaded per engine.

Tools by purpose: PdfPig = text layer and vector shapes; PDFium (PDFiumCore) = the only page renderer, decodes JBIG2 scans, one lock per process, hence helper processes; Tesseract 4.1.1 (`eng` fast for the first pass, `eng_best` for the second look); PdfSharp = writing the index; ENABLE word list + our terms = spelling.

## OCR and speed findings (measured 2026-11-23, i7-11850H 8C/16T, Bachman set on the P: share)

- Bachman: 266/380 sheets have zero text words; the title block is CAD stroke-font vector art, so OCR is the only source for those rows. A `|`/`II` from box borders, lost hyphens (`G-15` read as `G5`), split title lines and `GE NERAL` were seen with the current OCR path (600 DPI, default page-segmentation mode, three PNG round-trips).
- Current OCR path costs about 1.9 s/sheet sequentially (about 8 minutes for 266 sheets). A bench with 300 DPI, one render per sheet, line/block layout modes and `eng_best` took about 1.07 s/sheet single-threaded and 0.4 s/sheet with 4 workers (each with its own engine and its own Windows PDF document). 8 workers were no faster because Windows.Data.Pdf rendering contends.

- PdfPig text extraction (`open sheet`, about 83 ms/page) does not scale across threads with the default GC, but does with Server GC: 4 threads went from 31 s to 12.9 s for the Bachman set. Use Server GC plus one `PdfDocument.Open(byte[])` per worker over a shared byte array. **The csproj property is `ServerGarbageCollection`; the earlier `ServerGarbageCollector` spelling was silently ignored, so the app ran Workstation GC until 2026-11-24** (check the generated `*.runtimeconfig.json` for `"System.GC.Server": true`). With Workstation GC, stop-the-world pauses were more than half the run (28 s of 45 s in the bench); with Server GC about a fifth.
- The `total` timer includes the wait at the save-file picker. Real work for Bachman was about 41 s (scan 2 s, sheet loop 31 s, export 8 s).

## Early pipeline notes (2026-11-23; parts superseded, see section 6)

- Sheets are read on a number of worker threads chosen by the resource setting (see below; `ReadSheets` in `MainWindow.SheetReading.cs`, `Parallel.ForEach` over `Partitioner.Create(0, n, 1)` so work is handed out in page order). Each worker has its own PdfPig document (combined set: one shared `byte[]`, opened per worker), its own Windows PDF document cache and its own `OcrEngineSet`. Server GC is on in the csproj; PdfPig does not scale across threads without it.
- Text layer first. Blank fields only are OCR'd: one render of the needed field region per sheet at `OcrRenderDpi` (default 300), cropped per field. Windows can return a bitmap larger than requested (display scaling); `_ocrRenderScale` measures and corrects that, and crops are computed from the real bitmap size.
- One user-facing OCR setting: a preset (Fastest, Fast, Balanced (default), Quality, Ultra; `OcrPreset.cs`, stored as `OcrPreset` in settings.txt). The preset decides everything technical; DPI is fixed at 300 (`OcrPresets.RenderDpi`). Do not add per-field model choices to the UI; if a power-user mode is ever wanted, add an "advanced" toggle.
- Every preset reads sheets with the fast `eng` model (first pass). Thorough then takes a second look: after the whole index has been checked for patterns, only the fields still in doubt (flagged, or blank) are re-read with the large `eng_best` model (`SecondLook` in `MainWindow.SheetReading.cs`), and the index is assembled and checked again. Measured: reading every field with the large model costs about 1.6 s/sheet against 0.19 s for the fast model, and gained nothing on the checked sheets; escalating by confidence alone would re-read nearly every sheet ID (the fast model's ID confidence is rarely above 85), so escalation is driven by the pattern analysis instead. Engine start-up is about 50-160 ms and 20 MB per model, so holding both is cheap.
- `OcrImage.cs` cleans each crop (long lines and edge-touching arcs removed) and offers the variants (thicken, de-slant, darken). `OcrFieldRecognizer.cs` reads it: titles are read both thickened and thickened+de-slanted and the higher-scoring reading wins (a thin italic "II" was being dropped from plain reads); sheet IDs and disciplines are read untouched first, with extra variants only when doubtful. There are no hard rules about what a sheet number may look like (clients use quirky schemes): `OcrSetProfile.cs` learns the set's own shapes, prefixes, number widths, hyphen style and title punctuation from embedded text plus confident OCR, and `IndexAnalyzer.ChooseReadings` picks, among all readings of a field (`ReadAll` candidates from both models), the one that best fits that profile. ID readings are scored 0.35 x confidence + 0.40 x profile fit + 0.10 per extra pass that produced the same text + up to 0.20 for a series prefix other sheets also show (`CountPrefixRows`) - 0.30 when the reading is only part of another reading (`ScoreIdReading`). This fixed the "RMB-D-02 read as B-D-02" class of error: variants that lost the first letters scored more confidently because they were shorter.
- Windows PDF rendering is the speed floor of the old route: about 320 ms per sheet single-threaded and only about 1.3x faster with four threads, so 267 sheets take 60-80 s however many workers there are (measured without PdfPig or GC interference). It is capped at the resource plan's render concurrency (`RenderGate`).
- **Vector route (default first choice, 2026-11-24).** CAD plots draw title-block lettering as strokes. `PdfPigVectorSource.TryCollect` takes the sheet's paths (already parsed by PdfPig for the text check) and `VectorRaster.Render` draws the title-block region at 300 DPI straight into a `GrayImage` (round pen, alpha-composited in painter's order so white wipeouts hide what is under them; even-odd fills). Pen width is chosen from the letter height (`ChoosePenPoints`, about 9% of the median glyph height, 0.35-1.0 pt) because PdfPig's `LineWidth` is not scaled by the page transform. Declines (falls back to Windows rendering) when a picture covers the title block, there are no paths, or nothing visible is drawn; after reading, any field whose reading is blank/implausible is read again from a Windows render and the candidates are merged (`ReadFieldsCore`, `Preferred`). Counters: `OcrRunStats.VectorReads/WindowsReads/VectorFallbacks`, logged in `OCR summary:`. On the Bachman set (bench, 6 workers, Balanced): 196 sheets read from vectors, 26 fall back (a differently laid-out title block), 45 are scans (pictures) and use Windows; vector reading cost 28 s for the whole set against 60-80 s for Windows rendering, with reading quality at least as good. Not handled: clipping paths, dashes, pattern colours, text drawn as real glyphs (those pages have a text layer anyway). The second look (large model) still renders with Windows.
- `OcrIndexAnalysis.cs` (`IndexAnalyzer`, pure and unit-tested with real Bachman OCR rows) checks the assembled index for patterns: sheet numbers are repaired when sheets on both sides number consecutively across them, or extended from one neighbour when OCR's own reading is close; a different (confident) discipline blocks that, since it starts a new series; series letters are corrected to match the discipline ("RW-N-01" on MECHANICAL sheets -> "RW-M-01"); a discipline OCR could not read is inferred from the series letter. Title words are repaired from the set's own repeated words (split words, "NO.1", stray marks, near-miss spellings); only guesses are flagged. ## Resource setting

A second dropdown in Settings ("Computer resources": Background, Normal (default), High, Maximum; `ResourcePlan.cs`, stored as `ResourceLevel`). `HardwareProbe` reads logical processors, physical cores (`GetLogicalProcessorInformationEx`) and free memory; `ResourcePlanner.Plan` (pure, tested) turns level + hardware + sheet-set size into worker threads, concurrent sheet renders, a memory budget that caps the worker count (about 300 MB per worker) and the process priority, which is set for the run and restored afterwards. Levels scale with **physical** cores because measured throughput stops improving at about four workers and never improves past the physical core count (a 16-thread run with 15 workers was no faster than 6 workers): Background cores/4 (1-2), Normal cores/2 (2-4), High 3/4 of cores (3-6), Maximum all cores (2-8). Windows has no simple hard CPU cap, so the levels control threads, priority and the memory budget. `Program.cs` sets `OMP_THREAD_LIMIT=1` so each Tesseract engine is single-threaded. The plan is logged as `Resources - ...`; GC pause, full-collection count and bytes allocated per run are logged as `Memory management during this run`.

## Render helper processes (2026-11-24)

Windows' PDF renderer serialises the threads of one process: 120 sheets took 29 s on one thread and 26-28 s on four threads, whether they shared a file, used split files or one shared document object, but 12.6 s with four processes. So file locks are not the cause; concurrency needs processes. Render + OCR with N full-worker processes on one shared file (120 Bachman sheets): 1: 2.2 sheets/s; 2: 3.5; 3: 4.8; 4: 5.6; 6: 7.3; 8: 7.9 (the thread version reached 3.2).

Design: the program starts copies of itself as helpers (`MbrohDrawingIndexCreator.exe --render-helper`, handled at the top of `Program.Main` before any window exists; helpers get `DOTNET_gcServer=0`). `RenderPool` (pure, tested with fakes) starts helpers lazily on the first Windows render, reuses them for the whole run, returns null on any failure so the caller renders in-process (`RenderWindowsRegion` in `MainWindow.SheetReading.cs`, which falls back to `RenderGate` + `RenderRegionToGray`), and switches itself off after 4 failures. The protocol (`RenderProtocol`) is binary over the helper's stdin/stdout: path, page, page height, region, dpi in; gray bytes out. Helpers end when their input closes. Pool size per level (`ResourcePlan.RenderProcesses`, never more than the workers): Background 1, Normal min(cores/2, 4), High min(3/4 cores, 6), Maximum min(cores, 8) - conservative; raise after testing a set that needs many renders. The pool is created and disposed in `GenerateDrawingIndexCore`; the log line `Page-drawing helpers: N process(es) started, M page(s) drawn by them, K drawn in the main program instead` reports use.

Diagnostic inside the installed package (verifies child processes start under the package identity and that pictures match the in-process ones): `Invoke-CommandInDesktopPackage -PackageFamilyName <family> -AppId App -Command "<install dir>\MbrohDrawingIndexCreator.exe" -Args "--render-selftest <pdf> <resultFile> <pageHeight> <x1> <y1> <x2> <y2> [pages] [processes]"`; the result file ends with `RESULT: PASS` or `FAIL`.

## 2026-11-24 late morning: scans, spelling and writing conventions

- **Scans (JBIG2).** About half of the SHI scans (pages 338+) were not read because Windows.Data.Pdf draws some JBIG2 pictures as blank white pages (PdfPig cannot decode JBIG2 either). - **Spelling.** `dictionary\english-enable.txt` (ENABLE word list, public domain, 172k words) and `dictionary\drawing-terms.txt` (our additions) feed `OcrDictionary` (`dictionary\*.txt` are Content files; the tests copy them too). `Suggest` finds real words that differ only by confusable letters (groups O/Q/D/0, I/L/T/J/1, V/U/Y/W, N/M/H/A, E/F, C/G, S/5, Z/2, B/8, P/R; cost 0.4 each): one confusable letter is corrected with confidence (QZONE -> OZONE), two are corrected and flagged as a guess (AYDRAIED -> HYDRATED). A name that recurs across the set (BACHMAN) is only touched for one confusable letter. A real word is never snapped to a look-alike that merely recurs (this was turning OZONE back into QZONE); `IsKnownForFit` (used for title scoring) means a real word or a term seen on 3+ sheets that is not one confusable letter from a real word, so a misreading repeated across a series no longer counts as known and no longer wins on confidence. Split words are joined when the joined form is a real word and a piece is not (HE ADHOUSE -> HEADHOUSE).
- **Writing conventions** (`FlagTitles`, `RepairNumbersAfterNo`, `FlagRepeatedTitles`): possible misspelling (word neither real nor consistent), "NO." not followed by a number, stray single letters (I, V, X excluded as numerals), letters mixed with digits inside a word, a title starting or ending with a stray mark, a repeated word, and the same title on neighbouring sheets of one series. - **Off-position fields.** Single-line fields are read from a generous area and the nearest line is used; if that does not read as the field (not plausible / not confident), the next two nearest lines are read too and the analysis chooses by fit, skipping printed captions ("DWG", "NO."). A larger-overlap approach for title/discipline (classify lines by vocabulary and size) is the natural next step.

## 2026-11-24 evening: resolution findings, review step, more repairs

- **Seven-run analysis** (Balanced/Ultra at 300, 450, 600 DPI; `export_log.txt` `OCR page` lines are the final, post-analysis values). Higher DPI was worse: "still missing fields" 9-14 at 300 vs 17-23 at 450/600, IDs repaired from sequence 7 vs 13-15, titles refined 3 vs 14. Reason: Tesseract's recogniser rescales each line to its own fixed working height, so pixels beyond that add noise, time and worse layout analysis; our own pixel-based steps (line removal, `Thicken`, `Deslant`) were tuned at 300 DPI. Fix: `GrayImage.NormalizeLineHeight` (called from `OcrFieldRecognizer.Normalize` on every field image and every next-nearest line): measures the capital letter height (`TypicalLetterHeight`, upper quartile of ink-blob heights, robust to touching lines) and shrinks (area average, `Shrink`) when it exceeds `TargetLetterHeight` 34 px x 1.3. DPI is now a ceiling on drawing detail, not a recogniser setting. The log line `OCR image scale:` reports the average measured letter height and how many images were shrunk; use it to retune the target (if 300 DPI already averages under 44 px nothing is shrunk at 300).
- **Discipline vocabulary poisoning** (cause of "ARCHIT ECT URAL" at 450 DPI): confident OCR disciplines seen twice joined the known list as-is, so a repeated split reading became "known" and beat ARCHITECTURAL. `OcrVocabulary.LearnDisciplines` adds them most frequent first and skips any reading within 1-2 edits (ignoring spaces) of a known discipline. Scan disciplines that are unknown and not words are replaced by the discipline their sheet-number series uses (`CheckDisciplines`), with a reason.
- **Context repairs** (`OcrVocabulary.CorrectFromContext`, using `_titlePairs`, the count of titles containing each neighbouring word pair): a word on 2 sheets or fewer whose pairs occur nowhere, with a commoner word one edit away that pairs with the neighbours on 2+ sheets, is replaced (WAFER/WAILER/WAITER METER -> WATER METER; RUMP -> PUMP; ANK -> TANK; ROUGH -> TROUGH); a stray 1-2 letter token whose removal makes a known pair is dropped (letters that occur on 3+ sheets, such as A/B designators, are kept); `CND FLOOR` -> `2ND FLOOR`; long singleton non-words may snap up to 3 edits (FAYDRAIED -> HYDRATED); the fragment+tail join (`FATE ADHOUSE`) tolerates one wrong letter in a 6+ letter tail (`AE ADHQUSE`).
- **Lone zero** (`SetProfile.ZeroNumbersUnexpected`): when 8+ text-layer sheet numbers exist, none ends in 0 and most are 2+ digits wide, an OCR number ending in a lone `0` ("HLS-A-0", "RW-M-0") is no longer an anchor and is repaired from its neighbours (the thin trailing 1 of "01" was being lost in about 15 sheets per run).

## 2026-11-24 night, part 2: adaptive resolution (replaces "preset = DPI")

- **Why.** The user asked for a resolution scheme that holds up across sheet sizes, plot/scan quality and machines. - **Test lever for worker counts (diagnostics builds only):** `%TEMP%\AutoDIS\tuning.txt` with `workers=N` and/or `helpers=N` replaces the plan's counts (read in `ResourcePlanner.Plan`, lines marked `// DIAG`). - **Scan noise rules (`OcrVocabulary.DropStrayMarks`, `RefineTitle`):** a lone "I" after a word is dropped unless the set writes that word with a Roman numeral elsewhere (`_wordThenRoman`) or it follows "NO."; dropped mid-title it is silent, dropped from the end the title is marked guessed (flagged), because it may have been a real numeral. Lowercase one- or two-letter scraps ("oe", "i") in an otherwise capitalised title are dropped. A leading period/comma on a word (".PLAN") is stripped. ## Findings from the 2026-11-23 evening runs (four runs: Fastest/Maximum, Balanced/Maximum, Ultra/Maximum, Balanced/Normal)
