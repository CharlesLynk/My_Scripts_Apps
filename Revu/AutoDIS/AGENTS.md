# AGENTS.md — AutoDIS handoff

Read this first. It records what the project is, what has been changed, what the user is testing now, and what to do next.

## Purpose

AutoDIS (Mbroh Drawing Index Creator) is a WinUI 3 desktop app on .NET 10 (x64 only). It reads a set of drawing-sheet PDFs, OCRs each sheet's title block with Tesseract, extracts the sheet number, title, revision and related fields, and writes a drawing index PDF. Output is written atomically, so a locked target file is kept as a `.partial` file instead of being lost.

Packaging: MSIX (`Package.appxmanifest`), Package Name `d2bbdbd4-3016-443a-9f1f-e2344ac6a034`. The name must stay stable so upgrades install over the old package.

```
cd tests\AutoDIS.Tests; dotnet test
```

## Optimizations already made

1. Per-page word geometry cache (`WordGeometry`, `GetPageWordGeometry`, `BuildPageWordGeometry`). Removes repeated word extraction per page.
2. Memoized `MeasureWrappedHeight` (`WrappedHeightCache`).
3. Single-pass folder mode.

## OCR models (critical)

The 1.4.0.0 build shipped with **no `tessdata\` folder**, so Tesseract could not start and OCR silently never ran (DWU Bachman run, 2026-11-23: 266 of 380 sheets have no text layer and came out as `[NOT FOUND]`). The log line was `OCR unavailable (Tesseract engine init failed ...)`.

- `tessdata\eng.traineddata` (tessdata_fast) and `tessdata\eng_best.traineddata` (tessdata_best) are now in the project. They are byte-identical (SHA256) to the official upstream files and to the ones in the 1.3.4.0 baseline package under `reference\`, which is where to recover them from if they go missing again.
- **They are no longer committed.** `tessdata\` and `dictionary\english-enable.txt` are git-ignored. `OcrModels.targets` (imported by the app and test projects) downloads each file on the first build (tessdata_fast, tessdata_best, ENABLE word list), checks its SHA-256 and fails the build on a mismatch or failed download. To change a model, update its `Url` and `Sha256` there. A fresh clone needs internet on the first build only. `dictionary\drawing-terms.txt` stays tracked.
- Guards: the csproj fails the build if either file is missing; `Build-And-Install.ps1` checks the `.msix` contains both models plus `x64\tesseract41.dll` and `x64\leptonica-1.80.0.dll`; `OcrTests` starts the engine from the shipped models and reads rendered text.
- At run time the click handlers call `ConfirmOcrAvailableAsync` before the save picker (dialog: continue without OCR / cancel). `GenerateDrawingIndexCore` logs the engine state, counts sheets that needed OCR and that still had missing fields (`OcrRunStats`), and `ReportOcrOutcomeAsync` logs a summary and warns the user when OCR was needed but fell short. If the preferred model can't load, the other one is used and logged.
- Check `export_log.txt` (packaged: `%LOCALAPPDATA%\Packages\<package family>\LocalState\`) for `OCR engine ready` and `OCR summary:` after each run.

## OCR and speed findings (measured 2026-11-23, i7-11850H 8C/16T, Bachman set on the P: share)

- Bachman: 266/380 sheets have zero text words; the title block is CAD stroke-font vector art, so OCR is the only source for those rows. A `|`/`II` from box borders, lost hyphens (`G-15` read as `G5`), split title lines and `GE NERAL` were seen with the current OCR path (600 DPI, default page-segmentation mode, three PNG round-trips).
- Current OCR path costs about 1.9 s/sheet sequentially (about 8 minutes for 266 sheets). A bench with 300 DPI, one render per sheet, line/block layout modes and `eng_best` took about 1.07 s/sheet single-threaded and 0.4 s/sheet with 4 workers (each with its own engine and its own Windows PDF document). 8 workers were no faster because Windows.Data.Pdf rendering contends.
- Windows.Data.Pdf render cost is about 150 ms per crop regardless of crop size, so render once per sheet and crop.
- PdfPig text extraction (`open sheet`, about 83 ms/page) does not scale across threads with the default GC, but does with Server GC: 4 threads went from 31 s to 12.9 s for the Bachman set. Use Server GC plus one `PdfDocument.Open(byte[])` per worker over a shared byte array. **The csproj property is `ServerGarbageCollection`; the earlier `ServerGarbageCollector` spelling was silently ignored, so the app ran Workstation GC until 2026-11-24** (check the generated `*.runtimeconfig.json` for `"System.GC.Server": true`). With Workstation GC, stop-the-world pauses were more than half the run (28 s of 45 s in the bench); with Server GC about a fifth.
- The `total` timer includes the wait at the save-file picker. Real work for Bachman was about 41 s (scan 2 s, sheet loop 31 s, export 8 s).

## OCR pipeline (current design)

- Sheets are read on a number of worker threads chosen by the resource setting (see below; `ReadSheets` in `MainWindow.SheetReading.cs`, `Parallel.ForEach` over `Partitioner.Create(0, n, 1)` so work is handed out in page order). Each worker has its own PdfPig document (combined set: one shared `byte[]`, opened per worker), its own Windows PDF document cache and its own `OcrEngineSet`. Server GC is on in the csproj; PdfPig does not scale across threads without it.
- Text layer first. Blank fields only are OCR'd: one render of the needed field region per sheet at `OcrRenderDpi` (default 300), cropped per field. Windows can return a bitmap larger than requested (display scaling); `_ocrRenderScale` measures and corrects that, and crops are computed from the real bitmap size.
- One user-facing OCR setting: a preset (Fastest, Fast, Balanced (default), Quality, Ultra; `OcrPreset.cs`, stored as `OcrPreset` in settings.txt). The preset decides everything technical; DPI is fixed at 300 (`OcrPresets.RenderDpi`). Do not add per-field model choices to the UI; if a power-user mode is ever wanted, add an "advanced" toggle.
- Every preset reads sheets with the fast `eng` model (first pass). Quality and Ultra then take a second look: after the whole index has been checked for patterns, only the fields still in doubt (flagged, or blank) are re-read with the large `eng_best` model (`SecondLook` in `MainWindow.SheetReading.cs`), and the index is assembled and checked again. Measured: reading every field with the large model costs about 1.6 s/sheet against 0.19 s for the fast model, and gained nothing on the checked sheets; escalating by confidence alone would re-read nearly every sheet ID (the fast model's ID confidence is rarely above 85), so escalation is driven by the pattern analysis instead. Engine start-up is about 50-160 ms and 20 MB per model, so holding both is cheap.
- `OcrImage.cs` cleans each crop (long lines and edge-touching arcs removed) and offers the variants (thicken, de-slant, darken). `OcrFieldRecognizer.cs` reads it: titles are read both thickened and thickened+de-slanted and the higher-scoring reading wins (a thin italic "II" was being dropped from plain reads); sheet IDs and disciplines are read untouched first, with extra variants only when doubtful. There are no hard rules about what a sheet number may look like (clients use quirky schemes): `OcrSetProfile.cs` learns the set's own shapes, prefixes, number widths, hyphen style and title punctuation from embedded text plus confident OCR, and `IndexAnalyzer.ChooseReadings` picks, among all readings of a field (`ReadAll` candidates from both models), the one that best fits that profile. ID readings are scored 0.35 x confidence + 0.40 x profile fit + 0.10 per extra pass that produced the same text + up to 0.20 for a series prefix other sheets also show (`CountPrefixRows`) - 0.30 when the reading is only part of another reading (`ScoreIdReading`). This fixed the "RMB-D-02 read as B-D-02" class of error: variants that lost the first letters scored more confidently because they were shorter.
- Windows PDF rendering is the speed floor of the old route: about 320 ms per sheet single-threaded and only about 1.3x faster with four threads, so 267 sheets take 60-80 s however many workers there are (measured without PdfPig or GC interference). It is capped at the resource plan's render concurrency (`RenderGate`).
- **Vector route (default first choice, 2026-11-24).** CAD plots draw title-block lettering as strokes. `PdfPigVectorSource.TryCollect` takes the sheet's paths (already parsed by PdfPig for the text check) and `VectorRaster.Render` draws the title-block region at 300 DPI straight into a `GrayImage` (round pen, alpha-composited in painter's order so white wipeouts hide what is under them; even-odd fills). Pen width is chosen from the letter height (`ChoosePenPoints`, about 9% of the median glyph height, 0.35-1.0 pt) because PdfPig's `LineWidth` is not scaled by the page transform. Declines (falls back to Windows rendering) when a picture covers the title block, there are no paths, or nothing visible is drawn; after reading, any field whose reading is blank/implausible is read again from a Windows render and the candidates are merged (`ReadFieldsCore`, `Preferred`). Counters: `OcrRunStats.VectorReads/WindowsReads/VectorFallbacks`, logged in `OCR summary:`. On the Bachman set (bench, 6 workers, Balanced): 196 sheets read from vectors, 26 fall back (a differently laid-out title block), 45 are scans (pictures) and use Windows; vector reading cost 28 s for the whole set against 60-80 s for Windows rendering, with reading quality at least as good. Not handled: clipping paths, dashes, pattern colours, text drawn as real glyphs (those pages have a text layer anyway). The second look (large model) still renders with Windows.
- `OcrIndexAnalysis.cs` (`IndexAnalyzer`, pure and unit-tested with real Bachman OCR rows) checks the assembled index for patterns: sheet numbers are repaired when sheets on both sides number consecutively across them, or extended from one neighbour when OCR's own reading is close; a different (confident) discipline blocks that, since it starts a new series; series letters are corrected to match the discipline ("RW-N-01" on MECHANICAL sheets -> "RW-M-01"); a discipline OCR could not read is inferred from the series letter. Title words are repaired from the set's own repeated words (split words, "NO.1", stray marks, near-miss spellings); only guesses are flagged. Roman numerals are flagged, not rewritten, when they break the series (sets do have repeated numerals). Rows that still do not fit are flagged (orange) with reasons in the log.
- The set is copied to a local working folder once and the output is built locally and copied to its destination at the end (the network share was the slowest part of the export: 100 MB took about 4.6 s to write there against 0.15 s locally).
- `OcrTextCleanup.cs` (pure, unit-tested) cleans raw text: sheet-ID character fixes and hyphen insertion, discipline and title-word snapping to the vocabulary learned from the set.
- Uncertain OCR cells (`DrawingIndexItem.*Uncertain`) are highlighted orange in the index (`UncertainHighlightColor`); missing ones stay yellow. The CSV gets a CHECK column when any cell is uncertain. After a run the app shows a "Please review some entries" dialog and the log lists them (`OCR sheet needs review`, `OCR summary:`).
- Measured (bench, 300 DPI, Balanced): 34 Bachman text-layer sheets rendered and OCR'd: ID, discipline and title all 34/34. 18 stroke-font sheets with hand-checked answers: title 16/18, ID 16/18 before sequence repair, discipline 18/18; about 160 ms of OCR per sheet. The large model (Quality/Ultra) was 8-14x slower and not better on these clean vector sheets; it is untested on real scans, so validate on a scanned set before promising anything. Roman numerals ("II" vs "I") remain the weak spot; a series-based repair was tried and removed because sets legitimately repeat numerals.
- The Bachman set has unusually messy numbering; the target is about 95% exact with the rest flagged, not 100%.

## Resource setting

A second dropdown in Settings ("Computer resources": Background, Normal (default), High, Maximum; `ResourcePlan.cs`, stored as `ResourceLevel`). `HardwareProbe` reads logical processors, physical cores (`GetLogicalProcessorInformationEx`) and free memory; `ResourcePlanner.Plan` (pure, tested) turns level + hardware + sheet-set size into worker threads, concurrent sheet renders, a memory budget that caps the worker count (about 300 MB per worker) and the process priority, which is set for the run and restored afterwards. Levels scale with **physical** cores because measured throughput stops improving at about four workers and never improves past the physical core count (a 16-thread run with 15 workers was no faster than 6 workers): Background cores/4 (1-2), Normal cores/2 (2-4), High 3/4 of cores (3-6), Maximum all cores (2-8). Windows has no simple hard CPU cap, so the levels control threads, priority and the memory budget. `Program.cs` sets `OMP_THREAD_LIMIT=1` so each Tesseract engine is single-threaded. The plan is logged as `Resources - ...`; GC pause, full-collection count and bytes allocated per run are logged as `Memory management during this run`.

## Render helper processes (2026-11-24)

Windows' PDF renderer serialises the threads of one process: 120 sheets took 29 s on one thread and 26-28 s on four threads, whether they shared a file, used split files or one shared document object, but 12.6 s with four processes. So file locks are not the cause; concurrency needs processes. Render + OCR with N full-worker processes on one shared file (120 Bachman sheets): 1: 2.2 sheets/s; 2: 3.5; 3: 4.8; 4: 5.6; 6: 7.3; 8: 7.9 (the thread version reached 3.2).

Design: the program starts copies of itself as helpers (`MbrohDrawingIndexCreator.exe --render-helper`, handled at the top of `Program.Main` before any window exists; helpers get `DOTNET_gcServer=0`). `RenderPool` (pure, tested with fakes) starts helpers lazily on the first Windows render, reuses them for the whole run, returns null on any failure so the caller renders in-process (`RenderWindowsRegion` in `MainWindow.SheetReading.cs`, which falls back to `RenderGate` + `RenderRegionToGray`), and switches itself off after 4 failures. The protocol (`RenderProtocol`) is binary over the helper's stdin/stdout: path, page, page height, region, dpi in; gray bytes out. Helpers end when their input closes. Pool size per level (`ResourcePlan.RenderProcesses`, never more than the workers): Background 1, Normal min(cores/2, 4), High min(3/4 cores, 6), Maximum min(cores, 8) - conservative; raise after testing a set that needs many renders. The pool is created and disposed in `GenerateDrawingIndexCore`; the log line `Page-drawing helpers: N process(es) started, M page(s) drawn by them, K drawn in the main program instead` reports use.

Diagnostic inside the installed package (verifies child processes start under the package identity and that pictures match the in-process ones): `Invoke-CommandInDesktopPackage -PackageFamilyName <family> -AppId App -Command "<install dir>\MbrohDrawingIndexCreator.exe" -Args "--render-selftest <pdf> <resultFile> <pageHeight> <x1> <y1> <x2> <y2> [pages] [processes]"`; the result file ends with `RESULT: PASS` or `FAIL`.

## What each stage does (plain summary)

| Stage | Tool | What it does | Cost |
|---|---|---|---|
| Find text | PdfPig text layer | Reads embedded text inside each field box. Exact; no OCR. Parses the whole page's content to do so (not drawn). | about 100-300 ms/page, allocation-heavy |
| Draw the title block (CAD sheets) | PdfPig shapes + `VectorRaster` | Draws only the field boxes from the page's vector lines at the chosen DPI into a gray image. No PDF renderer. | about 40 ms/sheet |
| Draw the title block (scans, fallbacks) | Windows PDF renderer, in helper processes | Renders just the field area of a picture page. Windows still processes the whole page internally, so cost does not shrink with the area. | about 320 ms/page, parallel only across processes |
| Read the picture | Tesseract fast model (`eng`) | Reads each field from the image (cleaned: frame lines removed, line nearest the expected place kept, trimmed to the lettering, thickened/de-slanted variants). | about 100-300 ms/sheet |
| Backcheck (Quality/Ultra) | Larger Tesseract model (`eng_best`) on a 400 DPI redraw | Re-reads only entries still in doubt after the pattern check. | about 8-14x slower per field; used on few fields |
| Choose and repair | `IndexAnalyzer` (pure code) | Picks among readings by fit to the set, repairs numbering, numerals, split words, flags what does not fit. | milliseconds |
| Write the index | PdfSharp | Builds the index PDF/CSV. | seconds |

Only the field boxes (plus a search margin) are drawn or read. Single-line fields (sheet number, discipline) are cut with a margin of 60% of the box height (sheet number: also a sixth of its width) and the line of ink nearest the box centre is read, which tolerates lettering drawn a little off its box; lines cut by the margin edge are neighbours'' lettering and are passed over. If the field boxes lie far apart (union area over 3x the boxes'' total), each is drawn separately. Image resolution is a Settings choice (Automatic / 300 / 400 / 450 / 600 / 800 DPI, true DPI of the sheet at its printed size; stored as `OcrDpi`).

Position tolerance, next steps (not built): detect the enclosing cell of the template box from the sheet''s frame lines and snap to it; let the user define a second template for a page range whose title block is laid out differently; learn per-series offsets from sheets that read confidently and apply them to the series'' doubtful sheets.
## 2026-11-24 late morning: scans, spelling and writing conventions

- **Scans (JBIG2).** About half of the SHI scans (pages 338+) were not read because Windows.Data.Pdf draws some JBIG2 pictures as blank white pages (PdfPig cannot decode JBIG2 either). The new blank-page detector would have mislabelled them as blank. PDFium (`PDFiumCore` 4688, BSD, native `pdfium.dll` in the package; checked by `Build-And-Install.ps1`) decodes them and is also much quicker on CAD sheets (30-80 ms against 320 ms). `PdfiumRender` (one lock, because PDFium is not thread-safe) draws a region by matrix (PDFium maps the page to a top-left origin at 1 px per point first, so the matrix has no y flip); `PageRenderer` tries PDFium first, then Windows when PDFium is unavailable or finds no ink, and keeps the picture with more ink. Both the render helper processes and the in-process fallback use it. On the Bachman scans the fast model then read the sheet numbers and titles of every page tried; scan disciplines are still noisy (skewed frame lines survive the line removal).
- **Spelling.** `dictionary\english-enable.txt` (ENABLE word list, public domain, 172k words) and `dictionary\drawing-terms.txt` (our additions) feed `OcrDictionary` (`dictionary\*.txt` are Content files; the tests copy them too). `Suggest` finds real words that differ only by confusable letters (groups O/Q/D/0, I/L/T/J/1, V/U/Y/W, N/M/H/A, E/F, C/G, S/5, Z/2, B/8, P/R; cost 0.4 each): one confusable letter is corrected with confidence (QZONE -> OZONE), two are corrected and flagged as a guess (AYDRAIED -> HYDRATED). A name that recurs across the set (BACHMAN) is only touched for one confusable letter. A real word is never snapped to a look-alike that merely recurs (this was turning OZONE back into QZONE); `IsKnownForFit` (used for title scoring) means a real word or a term seen on 3+ sheets that is not one confusable letter from a real word, so a misreading repeated across a series no longer counts as known and no longer wins on confidence. Split words are joined when the joined form is a real word and a piece is not (HE ADHOUSE -> HEADHOUSE).
- **Writing conventions** (`FlagTitles`, `RepairNumbersAfterNo`, `FlagRepeatedTitles`): possible misspelling (word neither real nor consistent), "NO." not followed by a number, stray single letters (I, V, X excluded as numerals), letters mixed with digits inside a word, a title starting or ending with a stray mark, a repeated word, and the same title on neighbouring sheets of one series. A lost or misread number after "NO." is repaired from the other sheets with the same wording around it ("BASINS NO.# THRU 4" -> unanimous 1), else from the neighbouring titles (two apart, equal, or a look-alike digit that they make possible).
- **Off-position fields.** Single-line fields are read from a generous area and the nearest line is used; if that does not read as the field (not plausible / not confident), the next two nearest lines are read too and the analysis chooses by fit, skipping printed captions ("DWG", "NO."). A larger-overlap approach for title/discipline (classify lines by vocabulary and size) is the natural next step.
## 2026-11-24 afternoon: Windows renderer removed, more pattern repairs

- **PDFium is the only renderer.** `WinPdfRender`, `PageRenderer`, the Windows document cache and the `systemFactor` scaling were deleted (PDFium decodes the JBIG2 scans, is 4-8x quicker, and the Windows picture was only ever a fallback). Anything above that says "Windows rendering/Windows renders" now means a PDFium picture of the page ("drawn as pictures" in the `OCR summary:` line; counter `OcrRunStats.ImageReads`). `PdfiumRender.TryRegion` is called directly by `RenderRegionToGray` and by the helper processes (`RenderHelper.Serve`); `RenderRequest` lost its page-height field. The legacy page-border estimate (`EstimateBorderRectFromBitmap`) also draws with PDFium (100 DPI gray). `--render-selftest` now compares the helper pictures byte for byte with in-process PDFium pictures (args: pdf, result, pageHeight (unused), x1 y1 x2 y2, pages, processes). The pool still pays for scans (about 0.7 s per big picture, one lock per process).
- **Settings dialog** is wrapped in a `ScrollViewer` (the DPI box and new example box were below the visible area on smaller windows).
- **Fragment + tail of a frequent word** ("FATE ADHOUSE", "ALE ADHOUSE" for HEADHOUSE): `MergeSplitWords` joins a stray 1-4 letter fragment and a non-word piece that is the tail (or head) of exactly one word the set uses on 5+ sheets (`FindFrequentWord`).
- **Misplaced discipline/title** (`IndexAnalyzer.FixMisplacedFields`, runs right after `ChooseReadings`): a title that is exactly a discipline the set uses is not a title; the discipline is taken from it and the title from the best other reading of either field (title options plus discipline candidates) that is not a discipline. Reasons are added to the row.
- **Optional sheet number example** (Settings, session only, not saved): `SetProfile.UseExample` keeps only the character-kind signature (`HH-A-01` and `WT-A-104` both `A-A-0`). It sets `ExpectHyphen`, lifts `IdFit` for matching readings (0.5 + 0.5 learned) and lowers it for others (0.2 learned), and `FlagIdsOffFormat` flags OCR numbers of another format.
- Not done yet: user-editable index output (merge discipline groups, columns/rows per index sheet); text-size/orientation based classification (candidates carry no glyph size); vertical title blocks; reading scans from the embedded picture.
## 2026-11-24 evening: resolution findings, review step, more repairs

- **Seven-run analysis** (Balanced/Ultra at 300, 450, 600 DPI; `export_log.txt` `OCR page` lines are the final, post-analysis values). Higher DPI was worse: "still missing fields" 9-14 at 300 vs 17-23 at 450/600, IDs repaired from sequence 7 vs 13-15, titles refined 3 vs 14. Reason: Tesseract's recogniser rescales each line to its own fixed working height, so pixels beyond that add noise, time and worse layout analysis; our own pixel-based steps (line removal, `Thicken`, `Deslant`) were tuned at 300 DPI. Fix: `GrayImage.NormalizeLineHeight` (called from `OcrFieldRecognizer.Normalize` on every field image and every next-nearest line): measures the capital letter height (`TypicalLetterHeight`, upper quartile of ink-blob heights, robust to touching lines) and shrinks (area average, `Shrink`) when it exceeds `TargetLetterHeight` 34 px x 1.3. DPI is now a ceiling on drawing detail, not a recogniser setting. The log line `OCR image scale:` reports the average measured letter height and how many images were shrunk; use it to retune the target (if 300 DPI already averages under 44 px nothing is shrunk at 300).
- **Discipline vocabulary poisoning** (cause of "ARCHIT ECT URAL" at 450 DPI): confident OCR disciplines seen twice joined the known list as-is, so a repeated split reading became "known" and beat ARCHITECTURAL. `OcrVocabulary.LearnDisciplines` adds them most frequent first and skips any reading within 1-2 edits (ignoring spaces) of a known discipline. Scan disciplines that are unknown and not words are replaced by the discipline their sheet-number series uses (`CheckDisciplines`), with a reason.
- **Context repairs** (`OcrVocabulary.CorrectFromContext`, using `_titlePairs`, the count of titles containing each neighbouring word pair): a word on 2 sheets or fewer whose pairs occur nowhere, with a commoner word one edit away that pairs with the neighbours on 2+ sheets, is replaced (WAFER/WAILER/WAITER METER -> WATER METER; RUMP -> PUMP; ANK -> TANK; ROUGH -> TROUGH); a stray 1-2 letter token whose removal makes a known pair is dropped (letters that occur on 3+ sheets, such as A/B designators, are kept); `CND FLOOR` -> `2ND FLOOR`; long singleton non-words may snap up to 3 edits (FAYDRAIED -> HYDRATED); the fragment+tail join (`FATE ADHOUSE`) tolerates one wrong letter in a 6+ letter tail (`AE ADHQUSE`).
- **Lone zero** (`SetProfile.ZeroNumbersUnexpected`): when 8+ text-layer sheet numbers exist, none ends in 0 and most are 2+ digits wide, an OCR number ending in a lone `0` ("HLS-A-0", "RW-M-0") is no longer an anchor and is repaired from its neighbours (the thin trailing 1 of "01" was being lost in about 15 sheets per run).
- **Review step** (MainWindow.Review.cs, Settings checkbox, default on, saved): after reading and before export, ReviewEntries (called in GenerateDrawingIndexCoreInner right after the rows are assembled; it logs eview dialog (waiting for the user) to the diagnostics so run totals can be corrected) shows a dialog of discipline headings only (runs of consecutive rows with the same discipline). Each heading can be renamed or removed (joins the one above); headings, columns and pages re-flow when the index is built because they follow from the rows' disciplines. Undo and Reset-to-original buttons keep a snapshot stack. An eye icon per heading has a tooltip that draws, on first hover, the discipline+title area of up to three of its sheets (first doubtful, first, last) with PDFium (DrawFieldsPreview). The earlier per-entry editing section was removed at the user's request. Not done: a rendered page preview and column/rows-per-page controls.

## 2026-11-24 night, part 2: adaptive resolution (replaces "preset = DPI")

- **Why.** The user asked for a resolution scheme that holds up across sheet sizes, plot/scan quality and machines. Findings: (1) the reader shrinks every line to its own working height, so pixels beyond "letters about 44 px tall" add nothing measurable; (2) a scan has a native DPI (PdfPig `WidthInSamples` / bounding box; Bachman: 300) and rendering it much finer enlarges noise (good at 300-450, garbage at 600+); (3) a half-size print has half-size lettering, so a fixed DPI under-resolves it. So DPI is now derived, and presets differ by attempts (variants, retries, second look) plus a small oversampling headroom.
- **Vector sheets (Automatic DPI).** `DrawVectorField`: each wanted field is drawn on its own; a 150 DPI probe measures the letter height (`TypicalLetterHeight`), then the field is drawn at DPI = 150 x TargetLetterHeight x `OcrPresets.Oversample(preset, secondLook)` / measured (clamped 100-1200, field kept under `MaxFieldPixels` 24 MP). Oversample: Fastest 1.0, Fast 1.0, Balanced 1.25, Quality 1.5, Ultra 2.0, any second look 2.0. Average field DPI came out 330 at 1.0, 500 at 1.5, 630 at 2.0. Measured on the 32 hand-read vector sheets (Balanced, replayed): oversample 1.0-3.0 and fixed 300-800 DPI all gave 0-2 errors, i.e. indistinguishable with this sample; bench wall time 25 s (1.0) to 30 s (3.0). A fixed "Image resolution" choice in Settings still draws the union region at that DPI (testing lever).
- **Pictures (scans).** Preset DPI (`OcrPresets.FirstPassDpi`: 300/400/450/600/800) is now only a nominal ceiling: capped at 1.5 x the scan's own DPI (`NativePictureDpi`, min 200) and the drawn union region is kept under 48 MP.
- **Harness gotchas.** `%TEMP%\replay` must have the `dictionary` folder next to its exe, and must refine discipline counts with `vocab.RefineDiscipline` (otherwise the replay learns the broken variant). `vecbench` env: `EV_OVER` (oversample, per-field adaptive), `EV_MAX`, `EV_DPI`, `EV_TARGET`, `EV_TAG`.
